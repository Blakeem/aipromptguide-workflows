# debug

Flow maps show every agent, gate, loop and terminal state, generated by running the engine. See
**[review](FLOW-review.md)** here and **[develop](../develop/FLOW.md)** for the fix loop.

An autonomous Claude Code workflow that hardens a codebase as a planned campaign. First it builds a
verified inventory of real production defects, each scored for size. Once you triage it, the
[develop](../develop/) workflow fixes the approved issues behind a two-stage review and lands the
result on your branch, staged for you to commit or committed, as you chose at setup. The fix loop also
accepts an **external inventory** of findings from live/manual testing, a bug bash, or a symptom you
diagnosed yourself, so you can skip the review pass and go straight to fixing.

The two stages are the point. You cannot prioritize issues or estimate the work until the code is
reviewed, so `review.mjs` is read-only. It sweeps the codebase in bounded units concurrently so that the
sweep is fast. It then verifies every finding against the real code, scores each one, and writes one
issue file per unit.
Then it stops. You read those files, answer anything flagged for your decision, drop what you disagree
with. Each issue file is a fix-mode plan file, so develop then builds it behind a two-stage review.

Debug does **not** hunt a reported bug for you. There is no repro/bisect step. If you have a live symptom
("X crashes"), diagnose it first, then feed the result in as an external inventory (below).

### What sets it apart

This is a deliberately **lean** workflow. A default Claude workflow tends to spawn an agent for every
step. This one engineers those away and follows a strict set of principles:

- **No busy-work agents.** There is no loader, scribe, baseline, or organizer agent. Setup (the unit
  manifest, triage, a clean baseline) happens up front in the main session. No agent is spawned for a
  job the main session can already do.
- **The inventory travels verbatim.** Each unit's issue file is written once by the verifier and read
  byte-for-byte by the fixer and the acceptance gate. Nothing is parsed into fields and rebuilt, so
  nothing about a finding is lost or reinterpreted. There is no monolithic JSON inventory.
- **Two-stage review.** A blind critic reviews the first fix of each issue file and each later change
  that develop judges risky. It has no idea what issue the diff was meant to fix, so it catches a fix
  that solved the report but broke something else. Then an acceptance gate reads the issue, re-derives
  each defect's root cause and confirms it is fully closed with no regression. The gate also checks
  each of develop's risk judgments against that round's own changes.
- **The fix list is closed.** The fix loop only ever works the inventory you approved. No fresh
  review mid-fix keeps finding "just one more thing", which is what makes fixing medium issues
  converge instead of spiraling. For the same reason it hunts **defects only**. An improvement list
  never converges, and improvements would be auto-applied here. Those belong in
  [`enhance`](../enhance/).
- **Staging is the boundary unless commit mode is on.** Accepted fixes are staged. Only the acceptance gate
  stages, only on pass. In stage mode you do the commit. In commit mode the acceptance gate also commits
  each accepted block, or each packed pass of small issue files, as one commit. Develop's guide says how.
- **A fix that can't pass is parked, not discarded.** Its work is saved as a commit on a branch and
  cleared from the tree. The next issue file starts clean and nothing is thrown away. One entry in the
  project's backlog links the branch, so a later fix run can restore the work and finish it.

## Scope: is this the right tool?

This workflow reviews and hardens an existing codebase. It pays off when you want a thorough, verified
pass over a body of code, not a single targeted change:

- ✅ **Right size:** a production-readiness review of a codebase or a subsystem, where you want the
  issues found, triaged, and the approved ones fixed safely. It also fits a verified inventory (from
  manual testing) you want fixed the same way.
- ❌ **One bounded feature, or one goal spanning many call sites** (a migration, version upgrade, or
  framework port): write a plan file and build it with [`develop`](../develop/). Large, cross-cutting
  items this tool routes to DEFER make good `section` blocks there.
- ❌ **Nothing is broken and you want it *better*** (faster, simpler, cheaper, smaller): use
  [`enhance`](../enhance/). This workflow deliberately reports only what the code gets **wrong**. Its
  inventory drives an autonomous fixer, so an improvement list here would be applied automatically.

## How to use it

This workflow ships in the [AI Prompt Guide workflows](../../README.md) repo. Install the `aipg`
plugin once (`/plugin marketplace add Blakeem/aipromptguide-workflows` → `/plugin install
aipg@aipromptguide`), or clone the repo as `aipg/` and drive it by path. Then trigger it two ways:

- **Skill:** `/aipg:debug`, then *"review this repo for production readiness. Build is
  `<your build command>` and tests are `<your test command>`. Start with the review pass."*
- **Plain pointer:** tell Claude to *use the debug **workflow** in `aipg/workflows/debug/`* to review a
  target, with your build and test commands.

Either way Claude reads `aipg/workflows/debug/CLAUDE.md` and runs `gen-units.mjs`, `review.mjs`, then
develop's `develop-cycle.mjs` **by path**. The engines are in no global registry, so the folder pointer
is how they're discovered. There is nothing to build.

From there Claude drives everything:

1. **Splits the work.** It runs `gen-units.mjs` to divide your source tree into bounded review units,
   and shows you the unit list.
2. **Reviews it.** Reviewers run over every unit concurrently. A verifier follows only where findings
   exist (the reviewer marks clean units itself). One issue file per unit lands under
   `runs/<runId>/issues/`. Then it stops. Optionally you can give the pass one or more **lenses** to
   sweep the same code from several angles at once, such as a destructiveness audit, a data-loss sweep,
   or a compliance check. A lens narrows *which* defects matter and never turns the pass into a wish list.
3. **Walks you through triage.** Claude presents the inventory (totals, the hottest areas, every item
   that needs your decision) and helps you decide scope. You approve or skip issues by editing the
   issue files.
4. **Fixes it.** For each issue file, develop loops fixes and the two-stage review against that file
   unattended. It keeps the fix on acceptance. A file it cannot pass is parked
   with its work saved on a branch. Then Claude writes each issue's outcome back into its `status:` line.

A workflow runs in the background and **cannot ask you questions mid-run**, so Claude decides scope and
open questions with you between the two stages, not during them. Have it fix **one issue file** first
to check cost and quality before letting the rest go.

### Bring your own findings (skip the review pass)

The fix loop doesn't require the review pass. It only needs the issue files. When the findings come
from somewhere other than a code review (a **live testing session**, a bug bash, user reports, or a
symptom you diagnosed yourself), tell Claude to feed them into the debug workflow's fix loop. Claude writes
the per-unit issue files itself in the verifier's format (each finding anchored to `file:line` with the
evidence that confirmed it and a precise fix instruction, and anything you decline recorded as a SKIP so the
triage is on file), then runs develop on them as normal. Every safeguard still applies. Each issue is
re-confirmed against the current code before it is touched, every fix goes through the same two-stage review,
and accepted work lands the same way. Every entry marked ACTIONABLE is fixed, whatever
its severity.

Ask for an [exit survey](../../README.md#exit-survey) to have each agent of the run report on the workflow.

## The agents

Each is a fresh, throwaway context that does one job and returns one decision:

- **Reviewer** (review pass): reads one unit's files and reports production defects at or above your
  severity floor. It writes each finding and its evidence to a review file that the verifier reads.
  When the unit is clean, it writes that unit's clean-marker issue file instead.
- **Verifier** (review pass): confirms each finding against the real code, corrects inflated
  severity, and routes it (actionable, needs-your-decision, defer, or reject). It checks each fix it
  writes against the code that calls it and every place with the same rule. Then it writes the unit's
  issue file, where each issue records the evidence that confirmed it. That file is both the inventory
  and your triage document.
The fix loop is [develop](../develop/)'s, in fix mode. Its developer re-confirms each issue still
exists (stale ones are skipped, never re-fixed) and fixes only ACTIONABLE entries. A blind critic then
reviews the first fix and each later change the developer judges risky. An acceptance verifier
re-derives each root cause from the current code before it accepts the work. A fix that cannot pass within its
round budget is parked, with its work saved on a branch that one entry in the project's backlog links.

## Reviewing the result

In stage delivery nothing is committed and every fix is staged in your checkout. In commit delivery each
accepted block, or packed pass of small issue files, is one commit on your branch. A pass's commit
message is "pass of <ids>". Review it like a PR:

```bash
cd /path/to/repo
git diff --cached            # the run's fixes, beside anything you staged yourself (stage delivery)
git log --stat               # the run's commits (commit delivery)
<your build + test command>  # confirm green yourself
```

The run leaves a transparent trail under `runs/<runId>/`:

- `issues/<unit>.md`: the per-unit inventory and your triage document (the deliverable of the review
  pass). Read these to plan, and edit decisions in them.
- develop's run folder holds the fix loop's review files and declined findings. Its
  [README](../develop/README.md) lists them.

Run the gates yourself, spot-check the riskiest fixes, then commit (stage mode). Issues marked needs-attention
were attempted but not closed. The fix failed, its block stopped before acceptance staged it, or acceptance
found the fix incomplete. Read that block's acceptance review for why. Then work the parked block's
backlog entry, if it has one, or retry those issues with a sharper fix instruction.

## Requirements

- **Claude Code** with the Workflow capability.
- The target is a **git repository** (staging is how regressions are caught). The fix loop builds in a
  worktree of its own, so your uncommitted edits stay out of its review and you can keep working. Claude
  asks you to commit or set aside an edit only when it sits at a path a fix changed.
- Commands to **build and test** your project locally. You provide them. The workflow runs them and
  reads pass/fail. The fix loop only accepts a fix on green gates, so the suite should be green before
  you start.
