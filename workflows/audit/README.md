# audit

Flow maps show every agent, gate, loop and terminal state, generated by running the engine. See
**[defects](FLOW-defects.md)** and **[enhancements](FLOW-enhancements.md)** here, and
**[develop](../develop/FLOW.md)** for the fix loop.

An autonomous Claude Code workflow that audits a codebase in one of two kinds. Each kind has its own
product.

- **Defects** (the `/aipg:debug` skill) hardens a codebase as a planned campaign. First it builds a
  verified inventory of real production defects, each scored for size. Once you triage it, the
  [develop](../develop/) workflow fixes the approved issues behind a two-stage review and lands the
  result on your branch, staged for you to commit or committed, as you chose at setup.
- **Enhancements** (the `/aipg:enhance` skill) audits a system you **already have** for
  **enhancements**, the bigger changes worth writing up, not nits. It reports, and you decide. Nothing
  is applied automatically. Adopted proposals become blocks in a [`develop-cycle`](../develop/) plan
  file to get built.

The two products stay apart on purpose. The defects inventory drives an autonomous fixer, so an
improvement list there would be applied automatically. An enhancement list also never converges, since
there is always another enhancement. So the defects kind reports only what the code gets **wrong**, and
the enhancements kind hands every defect it finds back to you to route.

The defects fix loop also accepts an **external inventory** of findings from live or manual testing, a
bug bash, or a symptom you diagnosed yourself. This way you can skip the review pass and go straight to
fixing.

### What sets it apart

This is a deliberately **lean**, read-only audit built on the shared
[Workflow Principles](../../principles/). A default Claude workflow tends to spawn an agent for every
step. This one engineers those away:

- **No busy-work agents.** There is no loader, scribe, baseline, or organizer agent. Setup (the unit
  manifest, the scope and lenses, triage, a clean baseline) happens up front in the main session. No
  agent is spawned for a job the main session can already do.
- **Two stages in the defects kind.** You cannot prioritize issues or estimate the work until the code
  is reviewed, so the review pass is read-only. It sweeps the codebase in bounded units concurrently so
  that the sweep is fast. It then verifies every finding against the real code, scores each one, and
  writes one issue file per unit. Then it stops. You read those files, answer anything flagged for your
  decision, and drop what you disagree with. Each issue file is a fix-mode plan file, so develop then
  builds it behind a two-stage review.
- **The inventory travels verbatim.** Each unit's issue file is written once by the verifier and read
  byte-for-byte by the fixer and the acceptance gate. Nothing is parsed into fields and rebuilt, so
  nothing about a finding is lost or reinterpreted. There is no monolithic JSON inventory.
- **Two-stage review of every fix.** A blind critic reviews the first fix of each issue file and each
  later change that develop judges risky. It has no idea what issue the diff was meant to fix, so it
  catches a fix that solved the report but broke something else. Then an acceptance gate reads the
  issue, re-derives each defect's root cause and confirms it is fully closed with no regression. The
  gate also checks each of develop's risk judgments against that round's own changes.
- **The fix list is closed.** The fix loop only ever works the inventory you approved. No fresh
  review mid-fix keeps finding "just one more thing", which is what makes fixing medium issues
  converge instead of spiraling.
- **Staging is the boundary unless commit mode is on.** Accepted fixes are staged. Only the acceptance
  gate stages, only on pass. In stage mode you do the commit. In commit mode the acceptance gate also
  commits each accepted block, or each packed pass of small issue files, as one commit. Develop's guide
  says how.
- **A fix that can't pass is parked, not discarded.** Its work is saved as a commit on a branch and
  cleared from the tree. The next issue file starts clean and nothing is thrown away. One entry in the
  project's backlog links the branch, so a later fix run can restore the work and finish it.
- **Enhancement, not improvement.** The enhancements floor is deliberately high. A typo *is* an
  improvement, but nobody writes it up as an enhancement, and the defects kind catches it anyway.
  Every agent is held to one test, which asks whether a competent engineer would file the proposal as
  an enhancement ticket.
- **Removal is a first-class outcome.** Deleting a role, a file, an argument, or a code path is one of
  the best things an enhancements audit can return. The finders are told to hunt for it deliberately,
  because most audits only ever add.
- **Breadth, not slices, for enhancements.** Each finder reads the entire scope through its lens,
  because the best enhancements are cross-cutting ("every engine re-implements this", "these three
  roles could be two") and are invisible to anyone reading one file at a time.
- **A ruthless verifier.** The enhancements verifier first asks *does the system already do this?* A
  proposal for something the system already does is the most common failure of an audit pass. Then the
  verifier asks whether the claimed benefit is real, whether the proposal is only taste, and whether it
  is a **defect** in disguise. A noisy proposal list wastes your time, and an audit that cries wolf gets
  ignored.
- **Convergence is the signal.** Two lenses landing on the same change independently is the strongest
  evidence in an enhancements run. The lens files stay separate so you can see it.

## Scope: is this the right tool?

- ✅ **Defects, right size:** a production-readiness review of a codebase or a subsystem, where you want
  the issues found, triaged, and the approved ones fixed safely. It also fits a verified inventory (from
  manual testing) you want fixed the same way.
- ✅ **Enhancements, right size:** an existing, working system worth auditing from several genuinely
  different angles, such as making it faster, cheaper, simpler, smaller, harder to break, less work to
  operate, or newly capable.
- ❌ **A live symptom** ("X crashes"): neither kind hunts a reported bug for you, since there is no
  repro or bisect step. Diagnose it first, then feed the result in as an external inventory (below).
- ❌ **One bounded feature, or one goal spanning many call sites** (a migration, version upgrade, or
  framework port): write a plan file and build it with [`develop`](../develop/). Large, cross-cutting
  items the defects verifier routes to DEFER make good `section` blocks there.
- ❌ **You want creative options a human picks:** use [`brainstorm-cycle`](../brainstorm/).
- ❌ **You want the AI to conclude among competing approaches:** use [`decide-cycle`](../decide/).
- ➡️ **Then build:** adopted proposals become `feature` blocks in a [`develop-cycle`](../develop/) plan
  file (one block each), or `section` blocks for one goal spanning many call sites.

## How to use it

This workflow ships in the [AI Prompt Guide workflows](../../README.md) repo. Install the `aipg`
plugin once (`/plugin marketplace add Blakeem/aipromptguide-workflows` → `/plugin install
aipg@aipromptguide`), or clone the repo as `aipg/` and drive it by path. Then trigger it two ways:

- **Skill:** `/aipg:debug`, then *"review this repo for production readiness. Build is
  `<your build command>` and tests are `<your test command>`. Start with the review pass."* Or
  `/aipg:enhance audit this MCP server for efficiency, simplification, and operator effort`.
- **Plain pointer:** tell Claude to *use the audit **workflow** in `aipg/workflows/audit/`* for
  defects or for enhancements, with your build and test commands for a defects run.

Either way Claude reads `aipg/workflows/audit/CLAUDE.md` and runs `audit.mjs` **by path** with the
kind you asked for. A defects run also uses `gen-units.mjs` and develop's `develop-cycle.mjs`. The
engines are in no global registry, so the folder pointer is how they're discovered. There is nothing to
build.

A defects run goes through these steps:

1. **Splits the work.** Claude runs `gen-units.mjs` to divide your source tree into bounded review
   units, and shows you the unit list.
2. **Reviews it.** Reviewers run over every unit concurrently. A verifier follows only where findings
   exist (the reviewer marks clean units itself). One issue file per unit lands under
   `runs/<runId>/issues/`. Then it stops. Optionally you can give the pass one or more **lenses** to
   sweep the same code from several angles at once, such as a destructiveness audit, a data-loss sweep,
   or a compliance check. A lens narrows *which* defects matter and never turns the pass into a wish list.
3. **Walks you through triage.** Claude presents the inventory (totals, the hottest areas, every item
   that needs your decision) and helps you decide scope. You approve or skip issues by editing the
   issue files.
4. **Fixes it.** For each issue file, develop loops fixes and the two-stage review against that file
   unattended. It keeps the fix on acceptance. A file it cannot pass is parked
   with its work saved on a branch. Then Claude writes each issue's outcome back into its `status:` line.

An enhancements run goes through these steps:

1. **Frames it.** Claude agrees the scope and the lenses with you. Above all, it agrees what "better"
   *means* for this system, so the lenses optimize toward the same thing.
2. **Finds.** One finder per lens, concurrently, each reading the entire scope. Every candidate
   states what the code does today (with the line), what it would do instead, and the specific cost the
   change removes. It writes its candidates to a file, with the evidence for each.
3. **Verifies.** Verifiers check each candidate against the real code and reject what doesn't survive.
   Then they re-score impact and size and route the rest. Lenses with few candidates share a verifier,
   so a small audit spawns fewer agents.
4. **Stops.** Claude presents the proposals and triages them with you.

A workflow runs in the background and **cannot ask you questions mid-run**, so Claude decides scope and
open questions with you before and after each run, not during it. For a defects run, have it fix **one
issue file** first to check cost and quality before letting the rest go.

### Bring your own findings (skip the review pass)

The fix loop doesn't require the review pass. It only needs the issue files. When the findings come
from somewhere other than a code review (a **live testing session**, a bug bash, user reports, or a
symptom you diagnosed yourself), tell Claude to feed them into the defects fix loop. Claude writes
the per-unit issue files itself in the verifier's format (each finding anchored to `file:line` with the
evidence that confirmed it and a precise fix instruction, and anything you decline recorded as a SKIP so the
triage is on file), then runs develop on them as normal. Every safeguard still applies. Each issue is
re-confirmed against the current code before it is touched, every fix goes through the same two-stage review,
and accepted work lands the same way. Every entry marked ACTIONABLE is fixed, whatever
its severity.

Ask for an [exit survey](../../README.md#exit-survey) to have each agent of the run report on the workflow.

## The agents

Each is a fresh, throwaway context that does one job and returns one decision:

- **Reviewer** (defects): reads one unit's files and reports production defects at or above your
  severity floor. It writes each finding and its evidence to a review file that the verifier reads.
  When the unit is clean, it writes that unit's clean-marker issue file instead.
- **Verifier** (defects): confirms each finding against the real code, corrects inflated
  severity, and routes it (actionable, needs-your-decision, defer, or reject). It checks each fix it
  writes against the code that calls it and every place with the same rule. Then it writes the unit's
  issue file, where each issue records the evidence that confirmed it. That file is both the inventory
  and your triage document.
- **Finder** (enhancements): reads the entire scope through one lens and writes each candidate, with
  its evidence, to its lens's candidates file. A lens with no candidate writes its own clean proposal
  file.
- **Verifier** (enhancements): checks each candidate of its lenses against the real code, rejects what
  the system already does, re-scores impact and size, and writes each lens's proposal file.

The fix loop is [develop](../develop/)'s, in fix mode. Its developer re-confirms each issue still
exists (stale ones are skipped, never re-fixed) and fixes only ACTIONABLE entries. A blind critic then
reviews the first fix and each later change the developer judges risky. An acceptance verifier
re-derives each root cause from the current code before it accepts the work. A fix that cannot pass within its
round budget is parked, with its work saved on a branch that one entry in the project's backlog links.

## Reviewing the result

After a defects fix run in stage delivery, nothing is committed and every fix is staged in your
checkout. In commit delivery each accepted block, or packed pass of small issue files, is one commit on
your branch. A pass's commit message is "pass of <ids>". Review it like a PR:

```bash
cd /path/to/repo
git diff --cached            # the run's fixes, beside anything you staged yourself (stage delivery)
git log --stat               # the run's commits (commit delivery)
<your build + test command>  # confirm green yourself
```

The run leaves a transparent trail under `runs/<runId>/`:

- `issues/<unit>.md`: the per-unit inventory and your triage document (the deliverable of the review
  pass). Read these to plan, and edit decisions in them.
- `launch-<n>/`: one folder per launch. A launch of the review holds the reviewers' findings
  (`reviews/<unit>-<lens>.md`) and a copy of the issue files as they were before that launch
  (`kept/issues/`), so a re-review never replaces an earlier review or loses your triage edits.
- The fix loop's develop launches write in this same folder and take the next `launch-<n>/` numbers of
  the same sequence. develop's [README](../develop/README.md) lists their review files and declined
  findings.

Run the gates yourself, spot-check the riskiest fixes, then commit (stage mode). Issues marked needs-attention
were attempted but not closed. The fix failed, its block stopped before acceptance staged it, or acceptance
found the fix incomplete. Read that block's acceptance review for why. Then work the parked block's
backlog entry, if it has one, or retry those issues with a sharper fix instruction.

An enhancements run leaves `runs/<runId>/proposals/` with one file per lens, and one `launch-<n>/`
folder per launch that holds the finders' candidates (`candidates/<lens>.md`) and a copy of the proposal
files as they were before that launch (`kept/proposals/`). Each proposal file holds the kept
proposals (highest impact first), a `Defects to route` section when the verifier found a defect, and a
`Rejected` section that explains what was thrown out and why. Every proposal carries:

- **Today** states what the system does now, at a specific line
- **Instead** states the change, concrete enough to hand to a builder
- **Removes** names the specific cost it removes
- **Risk** states what it could break or make worse
- **impact / size / decision** holds the two scores and one of `ADOPT` (ready to build), `ROADMAP` (real,
  but needs planning), or `NEEDS_USER` (a call only you can make, with options and a recommendation)

Read the ADOPT items first, then decide scope. Each entry in the `Defects to route` section names a
defect, its file and line, and the evidence the verifier confirmed. Route it to a defects run.

## Requirements

- **Claude Code** with the background **Workflow** capability.
- The target is a **git repository** for a defects run (staging is how regressions are caught). The fix
  loop builds in a worktree of its own, so your uncommitted edits stay out of its review and you can
  keep working. Claude asks you to commit or set aside an edit only when it sits at a path a fix changed.
- Commands to **build and test** your project locally for a defects run. You provide them. The workflow
  runs them and reads pass/fail. The fix loop only accepts a fix on green gates, so the suite should be
  green before you start.
- An enhancements run needs only a repo or directory to audit, which is read **only**. Nothing is
  written to it, staged, or committed, and it needs no build or test commands, since it never runs your
  code.
